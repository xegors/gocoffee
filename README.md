# GoCoffee

> Терминальный backend магазина зерна спешалти-кофе на чистом Go, построенный по принципам Clean Architecture.

## Статус проекта

**Stage 1 «Foundation» — в работе.** Готовы шаги 0–5: домен (`Item`, `Money`,
`Wallet`, `User`, `Rank`, `Cart`), контракт `Payer` с оплатой кошельком и
первое хранилище — репозиторий каталога на `encoding/json`. Шаги 6–8: хранилище
пользователей, `ShopService`, точка входа.

## Что это

Учебный проект без продакшн-амбиций. Не кофейня, которая варит кофе в чашках, а
магазин зерна: каталог обжаренного кофе, мерч, аксессуары для заваривания,
наборы и слепые пакеты. Подписка на зерно вынесена в отдельный этап.

Корзина с FIFO-логикой, несколько способов оплаты, хранение в JSON.

Цель — не работающая программа, а понимание того, почему каждое решение
выбрано. Скорость поставки здесь вторична.

## Требования

Go 1.27 или новее. Внешних зависимостей нет — только стандартная библиотека.

## Быстрый старт

На данный момент доступны только проверки качества — запускать пока нечего,
точка входа появится на шаге 8:

```bash
gofmt -l .                  # должно быть пусто
go vet ./...                # должно быть тихо
~/go/bin/staticcheck ./...  # должно быть тихо, см. «Установка»
go test -race ./...         # тесты
go test -cover ./...        # домен 98.5%, storage 92.1%
```

Утилита `staticcheck` ставится отдельно:

```bash
go install honnef.co/go/tools/cmd/staticcheck@latest
```

`go run ./cmd/gocoffee` появится в конце Stage 1.

## Архитектура

Зависимости идут строго в одну сторону. Домен не знает ни о ком:

```text
cmd/gocoffee/main.go
        │
        ▼
internal/service ──────────► internal/domain ◄────────── internal/storage
        │                        ▲                             ▲
        └────────────────────────┴─────────────────────────────┘
                     main знает обо всех слоях
```

`storage` реализует контракты, объявленные в `service`. `domain` не импортирует
`encoding/json`: стандартная библиотека разрешена, формат хранения — нет.

## Структура

```text
gocoffee/
├── cmd/gocoffee/          # точка входа и сборка зависимостей
├── internal/
│   ├── domain/            # сущности и правила бизнес-логики
│   │   ├── item.go        # Item, Category
│   │   ├── money.go       # Money — целые рубли
│   │   ├── user.go        # User, Wallet (анонимное встраивание)
│   │   ├── rank.go        # Rank, Percent, RankFor — лояльность
│   │   ├── cart.go        # Cart = []CartItem, FIFO
│   │   └── errors.go      # ошибки домена
│   ├── storage/           # реализации репозиториев на encoding/json
│   │   ├── errors.go      # ошибки хранилища
│   │   ├── json_item.go   # каталог: DTO, ItemRepository, Load, Save
│   │   └── json_user.go
│   └── service/           # бизнес-логика поверх домена
│       ├── payer.go       # контракт Payer
│       ├── repository.go  # контракт ItemRepository
│       └── shop.go        # ShopService: AddToCart, RemoveFromCart, Checkout
├── data/                  # JSON-состояние, создаётся при первом запуске
└── go.mod
```

## Доменные модели

### Товар

```text
Item
├── ID           идентификатор-slug, уникален в каталоге
├── Name         название для показа
├── Category     категория, закрытый набор
├── Price        цена за упаковку, целые рубли
└── WeightGrams  масса нетто упаковки, 0 = неприменимо
```

### Категории

Набор закрытый и задан владельцем. **Набор товаров открытый, набор категорий —
нет:** новых позиций будет сотни, новых категорий не будет никогда. Именно
поэтому категория валидируется, а товар — нет.

| Значение | Что в неё |
|---|---|
| `coffee` | зёрна: имеет вес |
| `accessories` | воронки, фильтры, кофемолки |
| `sets` | наборы: цена фиксированная, состав не влияет на модель |
| `surprise` | слепой пакет: содержимое определяется при упаковке |

`merch` на Stage 1 нет: футболки и кружки с размерами и цветами требуют
вариантов товара, а это отдельная модель. Категория добавится на Stage 6.

### Деньги

`Money` — целые рубли. Цена `180` хранится как `180`, погрешности нет.
Именованный тип держит дисциплину: сложить рубли с количеством чашек не
получится.

### Кошелёк — шаг 2a, готово

```text
Wallet                User
└── Balance Money     ├── ID string
                      └── Wallet      ← анонимное встраивание значением
```

`Wallet` — одно поле, без бонусного баланса. Методы `Deposit` и `Withdraw`
принимают pointer-рецептор и при ошибке **не меняют баланс**: неудачная попытка
списания не должна постепенно съедать деньги. Ноль и отрицательные суммы —
ошибка, а не молчаливый no-op. Отрицательный баланс невозможен.

`User` пока несёт только `ID`. Email и логин появятся вместе с хранилищем
пользователей (шаг 6) и аутентификацией (Stage 2): поле, которое сейчас не
валидируется и не используется, — это заведённая дыра.

### Лояльность — шаг 2b, следующий

Код ещё не написан. Здесь зафиксирована модель, чтобы задание и реализация
опирались на одно решение.

```text
Rank — int, значение ранга равно его скидке в процентах

RankNone      0        потрачено 0— 3 999 ₽
RankBronze    3%       4 000 —   8 999 ₽
RankSilver    5%       9 000 —  19 999 ₽
RankGold      7%      20 000 —  49 999 ₽
RankPlatinum 10%      50 000 ₽ и выше
```

Ранг — чистая функция от суммы, потраченной за всё время: `RankFor(Money)`.
Поэтому он не может упасть, и хранить его в отдельном поле незачем.

Скидка применяется **на всю корзину**, а не на каждый товар, и округляется
**вниз** до целого рубля. Округление по позициям даёт другую сумму и
накапливается: на корзине из трёх товаров по 180 ₽ разница уже в 1 ₽.

### Корзина

`Cart` — срез `[]CartItem`. Порядок добавления сохраняется самим фактом среза;
дедупликация и удаление — линейные проходы.

### Оплата

`Checkout` принимает любой тип, удовлетворяющий контракту `Payer`. Контракт
объявлен в `service/payer.go`, потому что объявляет его потребитель, а не
домен. Домен пакет `service` не импортирует: `Wallet` удовлетворяет контракту
структурно, поэтому в `domain/user.go` нет ни одной ссылки на `Payer`.

Контракт состоит из одного метода `Pay(amount Money) error`. Метод `Name()`
появится на Stage 3 вместе с интерфейсом, когда платёжный способ надо будет
показать пользователю.

### Хранилище каталога — шаг 5, готово

`ItemRepository` объявлен в `service/repository.go` и состоит из `Load` и
`Save`. Реализация — `storage.ItemRepository`, путь к файлу приходит в
конструктор, а не в методы: `main` связывает конкретный путь один раз, и
контракт остаётся чистым.

`domain.Item` и `itemDTO` — разные структуры. Посредник нужен, чтобы `domain`
не импортировал `encoding/json`. Цена переносится без конвертации: `Money` —
это `int64`, в JSON это число. А вот `Category` в DTO лежит строкой: если бы
там стоял тип домена, `json.Unmarshal` записал бы в поле что угодно без
проверки, и `ParseCategory` не вызвался бы. Со строкой значение обязано пройти
через парсер.

Формат файла — голый JSON-массив с отступами, пустой каталог пишется как `[]`,
а не как `null`:

```json
[
  {
    "id": "ethiopia-chelchele-250",
    "name": "Ethiopia Chelchele",
    "category": "coffee",
    "price": 799,
    "weight_grams": 250
  }
]
```

## Принятые решения

| Решение | Почему | Чем платим |
|---|---|---|
| `Category` — закрытый набор с `Valid()` | Категории заданы владельцем и не меняются | Новая категория требует правки кода и теста |
| Набор товаров открыт, набор категорий закрыт | Товаров сотни, категорий четыре | Разные данные требуют разной строгости |
| Идентификатор — строковый slug | Доменный ID не совпадает с первичным ключом БД | Уникальность проверяется при загрузке |
| `WeightGrams` — поле `Item` | Проще, чем отдельные типы на категорию | Поле пустое у неприменимых категорий |
| Способ заваривания не хранится | Степень обжарки и способ заваривания — разные оси; фильтр и эспрессо не рекомендуем | Потеряна рекомендация «как варить» |
| Мерч вынесен на Stage 6 | Stage 1 не должен быть этапом для интернет-магазина | Возврат к задаче через пять этапов |
| `Money` — целые рубли | Целочисленная арифметика, путь к SQL без плавающей точки | Копейки не выражаются, проценты требуют округления |
| Скидка на всю корзину, округление вниз | По позициям ошибка копится: на трёх товарах по 180 ₽ разница уже в 1 ₽ | Кофейня теряет до рубля на корзину |
| Ранг хранит процент, а не имя | Соответствие «ранг = скидка» гарантировано типом | Названия рангов придётся держать в голове |
| Ранг не падает | Сумма копится за всё время, `RankFor` чистая функция | Потерять скидку за неактивность нельзя |
| Бонусного баланса нет, есть ранг | Два баланса без правил — второе число без смысла | — |
| `Cart = []CartItem` | FIFO бесплатно, порядок добавления сохраняется сам собой | Дедупликация и поиск — линейный проход |
| Анонимное встраивание `Wallet` в `User` | Плоский доступ без лишних полей | Промоушен полей неявен |
| `Payer` как интерфейс | Платёжная стратегия | Реализации подменяются без правок сервиса |
| `Payer` живёт в `service`, а не в `domain` | Объявляет потребитель: контракт описывает то, что нужно `Checkout` | Домен не знает о способах оплаты |
| `Wallet.Pay` делегирует `Withdraw` | Оплата и снятие денег — одна операция | Второе имя у той же операции; добавится при появлении других плательщиков |
| Крипта — конвертация по курсу в момент оплаты | Каталог один, вторая цена не хранится | Нужны `RateProvider`, правило округления, курс в заказе |
| Контракты объявляет потребитель | Dependency Inversion: домен не описывает то, чем пользуются другие | Больше типов, границы честные |
| Тесты пишутся вместе с кодом | Навык не закрепится, если отложить | Дисциплина в каждой задаче |
| DTO между доменом и JSON | Домен не знает про формат хранения | Две функции конвертации на каждую сущность |
| `Category` в DTO — строка | Иначе `json.Unmarshal` примет любое значение без парсера | Нужен парсер при каждой загрузке файла |
| Формат каталога — голый массив, без обёртки и версии | `json.Unmarshal` и так прощает забытые поля, а новые получат нулевое значение | Версию придётся заводить при первой миграции |
| Отсутствующий и пустой файл дают пустой каталог | Первый запуск не должен падать; файл пустой, если человек его стёр намеренно | Не отличить «файла нет» от «файл с данными, которые не распознались» |
| `Load` не создаёт файл, `Save` создаёт каталог | Чтение не должно иметь побочных эффектов | Каталог появится только при первой записи |
| Ошибки чтения и разбора различаются | `Permission denied` — не «битый каталог» | Нужен `switch` вместо одиночной проверки |
| Неизвестная категория валит всю загрузку | Частичный результат выглядит как «всё прочиталось», товар теряется тихо | Чинить файл придётся по одной позиции |
| `var _ service.ItemRepository = (*ItemRepository)(nil)` | Без этого расхождение подписей всплывёт в `main` на шаге 8 | Одна строка, ловит ошибку контракта на месте написания |

## Что осталось открытым

- **Подписка вынесена в отдельный этап.** Из неё вырастут регулярные списания,
  пропуск месяца и отмена — это самостоятельная подсистема, а не категория.
- **Мерч и варианты товара — Stage 6.** «Размер и цвет — тот же товар» означает,
  что в каталоге две сущности: товар и вариант. Пока вариантов нет, `Item` —
  это и есть покупаемая единица. Открытый вопрос к Stage 6: **одна ли цена у
  размеров M и L.** Если да, варианты обязательны; если у каждого своя цена,
  плоских товаров хватит.
- **`WeightGrams` — плоская структура.** Поле осмысленно только для зерна; у
  воронки и набора оно пустое. Разделять типы по категориям рано: это
  полиморфный каталог, который потребует дискриминатора типа в JSON. Пересмотр
  назначен на Stage 7 вместе с переходом на базу. Степень обжарки, метод
  обработки и страна происхождения добавятся на Stage 3 и сделают этот долг
  заметнее: к тому моменту у `Item` будет около пятнадцати полей, из которых
  осмысленно заполнены только у зерна.
- **Цена за упаковку, а не за килограмм.** Предполагается, что `WeightGrams`
  описывает упаковку, а `Price` — цену этой упаковки. Если понадобится цена за
  килограмм, это отдельное решение.
- **Пороги рангов меняются по опыту.** 4 000 / 9 000 / 20 000 / 50 000 ₽ взяты из
  среднего чека 2–5 тысяч в месяц. Реальные цифры станут видны после первых
  заказов, и тогда же проверить, достаточно ли мотивации.
- **Что делать с `Email`.** Пока у `User` только `ID`. Формат адреса не
  определён, а поле без валидации пропустит мусор незамеченным. Решение — на
  шаге 6 вместе с хранилищем пользователей.
- **Совместный заказ.** `Cart.Merge` объединяет две корзины, но правил покупки
  вдвоём нет. До реализации `Checkout` (шаг 7, не позже Stage 4) решить: один
  кошелёк платит или два, чей ранг даёт скидку, можно ли разделить оплату между
  участниками и кто владеет объединённой корзиной. Скидка не согласована со
  сложением корзин: округление вниз не раскидывается по сумме, поэтому
  «скидка на объединённую корзину» и «скидки каждого отдельно» дают разные
  деньги.
- **Слой `presentation`.** Появится на Stage 2.
