# GoCoffee

> Терминальный backend виртуальной кофейни спешалти-кофе на чистом Go, построенный по принципам Clean Architecture.

## Статус проекта

**Stage 1 «Foundation» — в работе.** Кода пока нет: идёт разработка доменного слоя.

|---|---|

## Что это

Учебный проект без продакшн-амбиций. Backend виртуальной кофейни: каталог,
корзина с FIFO-логикой, несколько способов оплаты, хранение в JSON.

Цель — не работающая программа, а понимание того, почему каждое решение
выбрано. Скорость поставки здесь вторична.

## Требования

Go 1.27 или новее. Внешних зависимостей нет — только стандартная библиотека.

## Быстрый старт

На данный момент доступны только проверки качества:

```bash
gofmt -l .      # должно быть пусто
go vet ./...    # пока предупреждает «no packages» — это ожидаемо
```

Запуск приложения (`go run ./cmd/gocoffee`) появится в конце Stage 1.

## Архитектура

Зависимости идут строго в одну сторону. Домен не знает ни о ком:

```text
cmd/gocoffee/main.go
        │
        ▼
internal/service ──────────► internal/domain ◄────────── internal/storage
        │                        ▲                             ▲
        └────────────────────────┴─────────────────────────────┘
                     main знает обо всех слоях
```

`storage` реализует контракты, объявленные в `service`. `domain` не импортирует
ничего, кроме стандартной библиотеки.

## Структура

```text
gocoffee/
├── cmd/gocoffee/          # точка входа и сборка зависимостей
├── internal/
│   ├── domain/            # сущности и правила бизнес-логики
│   │   ├── user.go        # User, Wallet (анонимное встраивание)
│   │   ├── cart.go        # Cart = []CartItem, FIFO
│   │   ├── item.go        # Item, Category
│   │   ├── payment.go     # контракт Payer
│   │   └── errors.go      # ошибки домена
│   ├── storage/           # реализации репозиториев на encoding/json
│   │   ├── json_user.go
│   │   └── json_item.go
│   └── service/           # ShopService: AddToCart, RemoveFromCart, Checkout
├── data/                  # JSON-состояние, создаётся при первом запуске
├── docs/
│   └── decisions/         # записи архитектурных решений
└── go.mod
```

## Доменные модели

**User и Wallet.** `User` анонимно встраивает `Wallet` — доступ плоский
(`user.Balance`), структура составная. Обратная сторона: промоушен полей
теряется при маршалинге в JSON, поведение неявное.

**Корзина FIFO.** `Cart` — это срез `[]CartItem`. Порядок добавления сохраняется
самим фактом среза; дедупликация и удаление — линейные проходы.

**Платёжная стратегия.** `Checkout` принимает любой тип, удовлетворяющий
интерфейсу `Payer`. Контракт живёт в `domain/payment.go`, реализация кошелька —
рядом с `Wallet` в `user.go`.

## Принятые решения

| Решение | Почему | Чем платим |
|---|---|---|
| `Cart = []CartItem` | FIFO бесплатно, порядок добавления сохраняется сам собой | Дедупликация и поиск — линейный проход |
| Анонимное встраивание `Wallet` в `User` | Плоский доступ без лишних полей | Промоушен полей неявен и теряется при JSON-маршалинге |
| `Payer` как интерфейс | Платёжная стратегия: кошелёк, карта, крипта | Реализации подменяются без правок сервиса |
| Контракты объявляет потребитель, а не `domain` | Dependency Inversion: домен не описывает то, чем пользуются другие | Больше типов, но границы слоёв честные |
| Тесты пишутся вместе с кодом | Навык не закрепится, если отложить на потом | Дисциплина в каждой задаче |

## Открытые вопросы

Эти решения ещё не приняты, код доменного слоя не написан:

- **Идентификатор товара.** `int64` в домене, строковый slug или идентификация по
  имени. Влияет на корзину, заказы и таблицу `items` на Stage 5.
- **Деньги: `float64`.** Долг зафиксирован: `19.90 * 3 = 59.700000000000003`.
  Проверка точности — задача Stage 1, сравнение сумм в `Checkout` — там же.
- **Границы домена и JSON.** Теги `json:"..."` в `domain` или отдельные DTO
  в `storage`.
- **Категория товара.** Что происходит, если в `items.json` попадётся значение,
  которого нет среди известных.
- **Слой `presentation`.** Появится на Stage 2. До тех пор его в структуре нет.
